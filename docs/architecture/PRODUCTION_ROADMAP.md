## Phase 2 — GitHub-style milestones

Work is ordered by user trust. Previously verified critical fixes remain protected by regression tests and are not reimplemented.

### Milestone 1 — Data Integrity & Truthful Confirmations

1. **DI-01: Enforce monotonic, record-aware odometer updates**
   - Affected: `DashboardScreen.tsx`, `database.ts`, schema migration, validation utility/tests.
   - Acceptance: malformed/negative/lower-than-confirmed/lower-than-recorded values do not write; the modal stays open with a useful error; equal/higher values and predicted confirmation work; existing inconsistent profiles are repaired upward without deleting logs; reminders resync only after a committed write.
   - Tests: pure boundary tests, database-trigger/migration tests where available, Android reproduction at service 100/120 then attempted ODO 50.
   - Rollback: remove UI enforcement only if necessary; keep a backup before reverting database cleanup/trigger migration. Never restore rollback behavior silently.
2. **DI-02: Reject negative inventory at UI and database boundaries**
   - Affected: `InventoryScreen.tsx`, `database.ts`, validation utility/tests.
   - Acceptance: blank means zero; negative, decimal, partial, and unsafe integers are rejected inline; zero and positive whole quantities save; increment/decrement never cross zero; legacy negative rows become zero/Out.
   - Tests: parser/status/unit tests and Android add/decrement checks.
   - Rollback: UI can revert independently; schema guard should remain unless a migration incompatibility is proven.
3. **DI-03: Validate manual-reading domains everywhere**
   - Affected: `VehicleVitalsScreen.tsx`, settings display, `database.ts`, validation/tests.
   - Acceptance: percentage fields accept only 0–100; remaining numeric fields accept only documented storage domains (not recommended vehicle specs); errors are visible; invalid service/restore writes reject atomically; legacy invalid percentages are clamped to the nearest valid data-domain boundary.
   - Tests: field boundary matrix, partial-update tests, invalid-backup rejection.
   - Rollback: retain persisted data and remove only a disputed non-percentage bound; percentage invariants must remain.
4. **DI-04: Separate reading drafts from persisted display state**
   - Affected: `VehicleVitalsScreen.tsx`.
   - Acceptance: Cancel restores the last loaded values immediately; Back/revisit and vehicle switch show persisted values; successful save refreshes the persisted snapshot; failed save keeps an editable draft and shows failure.
   - Tests: extracted reset/state tests if practical plus Android edit/cancel/save/failure smoke.
   - Rollback: revert the screen state change without touching database data.
5. **DI-05: Remove unobservable share-success claims**
   - Affected: `export.ts`, `VehicleSettingsScreen.tsx`, export tests.
   - Acceptance: the app confirms file creation, never claims delivery; when sharing is available it says the share sheet closed and the local file remains; when unavailable it reports the saved location; JSON and CSV behave identically.
   - Tests: share available/unavailable adapter tests and Android cancel/share-sheet smoke.
   - Rollback: retain truthful “file created” copy even if the sharing abstraction is reverted.
6. **CB-06b: Persist service-history setup and explicit baseline knowledge**
   - Affected: types/schema/migrations, database and maintenance transactions/selectors/tests, `ServiceHistoryWizard.tsx`, `MaintenanceScheduleScreen.tsx`, backup format/tests; delete the unused duplicate wizard.
   - Acceptance: completion/Skip All persists per vehicle and survives restart/switch; each interval explicitly records whether its odometer baseline is known; a known zero is distinct from unknown; date-only history is reachable, validated, saved without starting a mileage counter, and survives backup/restore; linked deletion recomputes both baseline value and knowledge.
   - Tests: migration, transaction/delete, selector, backup v1/v2/v3, date, restart/vehicle-switch Android smoke.
   - Rollback: export a records backup first; migration columns are additive, so old code can ignore them. Do not destructively downgrade the database.

Milestone 1 gate: typecheck, full unit suite, lint, Android focused smoke for all six tasks, log scan for new warnings/fatals, and regression search across every database writer and every maintenance selector consumer.

## Additional findings

These were discovered while mapping and executing the audit. Only the High findings explicitly approved for Milestone 2 were implemented; Medium findings remain roadmap-only:

1. **High — backup validation was structurally shallow (approved and complete as AF-H01).** Earlier formats were accepted when `vehicle_profiles` was an array, while row shapes, vehicle references, numeric domains, and active vehicle validity were mostly trusted. Holistic validation now runs before destructive restore and is covered by rollback tests.
2. **High — service/fuel entries could exceed the profile odometer (approved and complete as AF-H02).** The prior UI permitted records above the confirmed vehicle reading, creating the inverse inconsistency of DI-01. Forms, service boundaries, triggers, and restore validation now reject the record with a clear “update odometer first” path rather than silently advancing confirmed mileage.
3. **Medium — async loading failures can leave spinners or surface as empty lists.** This is a concrete expression of REL-03 across Inventory, Readings, Fuel, and other screens. Recommendation: address systematically with shared loading/error states in Milestone 2 rather than ad hoc in Milestone 1.
4. **Medium — database creation DDL still describes the original singleton schema and relies on later migrations to reach the current multi-vehicle shape.** Recommendation: after transactional migration coverage exists, make fresh-schema creation match the latest schema to reduce drift; keep upgrade migrations for existing users.
5. **Medium — installed Expo package patch versions do not exactly match the SDK's expected versions.** Expo reports compatibility warnings for several packages during local startup. Recommendation: align the reported patch versions in a dedicated dependency-update change, rebuild the native clients, and rerun the full device matrix. This was not changed during the data-integrity milestone because dependency churn is unrelated and can alter native behavior.
6. **High — app-lock relock unmounted in-progress system-picker flows (approved and complete under the “High only” Milestone 2 scope).** Returning from Android photo/document pickers correctly triggered the background lock, but the auth route replaced the protected navigator and discarded the form draft. The protected navigator now stays mounted; protected native modals withdraw while locked, and a fully opaque native lock occupies the top layer. Unlocking resumes the exact workflow without exposing records.
7. **High — the legacy app icon was not square (approved and complete).** `assets/icon-v2.png` is now a square production-size source derived from the existing mark, `app.json` uses it, and Expo Doctor passes. Adaptive launcher and splash identity are completed separately below.
8. **High — the dependency tree contained a Critical advisory (Critical removed; residual risk documented).** SDK-compatible overrides removed the `shell-quote` Critical advisory. The Android production graph still reports 32 lower-severity transitive findings (21 high, 10 moderate, 1 low), primarily Expo/React Native build-tool chains; npm's proposed blanket remediation crosses Expo SDK compatibility. Recommendation: retain the zero-Critical release gate, re-triage on every supported Expo upgrade, and do not run forced incompatible remediation.
9. **Medium — the Android adaptive icon and splash used starter-style artwork (approved and complete).** Candidate 2 removes the template grid layers, uses the existing blue 3azza mark for adaptive foreground, monochrome, and splash rendering, and uses the product navy as the adaptive/splash background. Generated resources, launcher masking, the Android splash animation, preserved-data upgrade, and cold-launch logs were verified on API 35. The logo itself was not redesigned.
10. **Low — native vendor code emits deprecation and future Gradle compatibility warnings (not approved).** The release build succeeds and runtime logs are clean, but Expo/React Native dependencies warn about deprecated APIs and future Gradle 10 compatibility. Recommendation: re-evaluate during the next supported Expo SDK upgrade instead of editing generated/vendor code.
11. **Low — the first local native release build is memory-intensive (not approved).** Gradle reported constrained JVM/metaspace conditions during the successful first build. Recommendation: reproduce in CI and configure project-level Gradle memory only if the supported build environment remains constrained; do not tune generated files ad hoc.
12. **High — maintenance progress and several layouts relied on viewport assumptions (user-approved and complete).** Home used `odometer % 10,000` as a decorative gauge rather than the selected maintenance interval, native SVG positioning was implicit, the tab bar overlaid content, and Documents mixed percentage widths with absolute actions. This made a nearly due service look far away and clipped or split content on the physical Samsung. Recommendation implemented: share the planner's interval math, derive visual geometry from the measured viewport/container, keep navigation and actions in normal layout flow, and preserve only semantic fixed control/icon sizes. Physical version-code-4 evidence and the automated gate are recorded above.
